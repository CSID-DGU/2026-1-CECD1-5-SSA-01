# ERCE 팀 작업 가이드

## 1. 작업 목표

ERCE는 법안의 비용추계 초안을 만드는 신규 엔진이다. 기존 엔진을 통합하거나 수정하는 작업이 아니다.

핵심 구조는 다음과 같다.

```text
법안 원문
  → AI가 비용 유발 요인과 세부 유형 판단
  → 등록된 고정 산식 선택
  → 법안 명시값·실제자료·공식 기준·검토된 선례에서 변수 선택
  → 결정론적 계산
  → 근거와 가정을 포함한 검토용 추계 초안
```

AI의 역할은 법안을 읽고 비용유형을 분류하며 변수 후보의 적용 가능성을 판단하는 데까지다.
AI가 산식을 새로 만들어 선택하거나, 출처 없는 숫자를 생성해 빈 변수를 채우면 안 된다.

## 2. 작업 범위

신규 작업은 다음 폴더에서만 진행한다.

```text
backend/erce/
├── engine.py                       # 실행 진입점
├── route_tree.py                   # 비용유형·세부유형 라우팅 트리
├── formula_registry.py             # 라우팅 결과와 고정 산식 연결
├── variable_resolver.py            # 변수 우선순위와 누락 판정
├── variable_evidence_store.py      # 로컬 변수 근거 DB 저장·조회
├── *_evidence*.py                  # 검토된 변수·단가 근거
├── scripts/
│   └── build_variable_table.py     # 로컬 변수 DB 재구축
└── tests/                          # ERCE 회귀 테스트

docs/erce/
├── ERCE_ROUTE_TREE.md              # 현재 라우팅·산식 구조
├── ERCE_VARIABLE_TABLE.md          # 변수 DB 정책
├── ERCE_TEAM_WORK_GUIDE.md         # 본 문서
└── cases/                          # 의안별 최초 결과와 보강 기록
```

기존 `engine_v7.py`, `finale_engine.py`, `committee_*`, `estimator_v2/` 등은 과거 실험·참고용이다.
ERCE 작업을 위해 이 파일들을 이동하거나 합치거나 수정하지 않는다.

현재 ERCE가 계산에 사용하는 다음 파일은 공통 계산 기반이므로 함께 필요하다.

- `backend/general_cost_resolver.py`
- `backend/economic_forecast_registry.py`
- `backend/research_service_unit_cost_registry.py`

## 3. 최초 실행

저장소 루트에서 실행한다.

```bash
python3 -m backend.erce.scripts.build_variable_table
python3 -m unittest discover -s backend/erce/tests -p 'test_*.py' -v
```

로컬 DB는 `backend/generated/erce_variable_evidence.sqlite3`에 생성된다. 생성 DB는 Git에 올리지 않는다.

## 4. 팀원 작업 단위

한 사람은 한 번에 하나의 비용유형만 담당한다. 서로 다른 유형을 한 작업에 섞지 않는다.

예시:

- 이전지출/개인지원 5건
- 물건비/연구용역 5건
- 자본지출/자산취득 5건

의안은 개발용 자료에서 선택한다. `backend/fixtures/general_cost_seven_type_holdout.json`에 포함된
의안은 최종 검증용이므로 산식·변수·단가 개발에 사용하지 않는다.

## 5. 의안 한 건의 작업 순서

### 1단계: 정답을 가리고 입력 확인

비용추계서 정답을 열지 않고 법안 원문과 제안 이유만 확인한다. 다음 내용을 추출한다.

- 비용을 발생시키거나 수입을 감소시키는 조항
- 대상, 수량, 시행일, 적용 기간
- 법안에 직접 명시된 값
- 실제자료나 공식 기준을 추가로 확인해야 하는 값

### 2단계: 비용유형 라우팅

`backend/erce/route_tree.py`에서 정확한 말단 경로를 선택한다.

```text
상위 비용성격 → 사업·서비스 유형 → 계산 방식 → route_key
```

그룹까지만 선택하고 임의 산식을 적용하면 안 된다. 적절한 말단이 없다면 `미등록`으로 기록한다.

### 3단계: 고정 산식 확인

선택한 `route_key`가 `formula_registry.py`의 산식과 정확히 연결되는지 확인한다.

- 산식이 있으면 그대로 사용한다.
- 산식이 없으면 정답 금액이 아니라 반복 가능한 비용 발생 구조를 보고 새 말단 산식을 추가한다.
- 비슷해 보인다는 이유로 `수량 × 단가` 같은 일반 산식으로 강제 대체하지 않는다.

### 4단계: 변수 후보 선택

변수는 다음 우선순위로 채운다.

1. 법안에 명시된 값
2. 대상 기관·사업의 실제자료
3. 적용 가능한 공식 기준과 공식 단가
4. 앞 단계에서 계산되어 검증된 값
5. 검토된 선례의 가정

선례 후보는 변수 DB에서 찾되 자동으로 가장 유사한 값이라고 간주하지 않는다. AI가 다음 조건을 확인한다.

- 업무 목적과 범위
- 대상 집단과 기관
- 전국·지역 등 사업 규모
- 원/명, 원/회, 원/년 등 단위와 시간 기준
- 포함된 세부 비용
- 가격 기준연도와 적용연도
- 공개일이 현재 법안보다 이전인지

조건이 맞지 않으면 후보를 제외한다. 적절한 값이 없을 때는 숫자를 임의 생성하지 않고 `근거 부족`으로 남긴다.

### 5단계: 최초 결과 고정

정답을 보기 전에 다음 내용을 `docs/erce/cases/ERCE_CASE_{의안번호}.md`에 기록하고 저장한다.

```markdown
# ERCE 사례: {의안번호}

- 담당 비용유형:
- 선택한 route_path / route_key:
- 선택한 산식:
- 사용한 변수·값·단위:
- 변수별 출처:
- 제외한 후보와 이유:
- 누락 변수:
- 최초 연도별 추계액:
- 최초 합계:
- 최초 결과 저장 시각:
```

이 기록이 끝나기 전에는 정답 비용추계서를 열지 않는다.

### 6단계: 정답 비교

최초 결과를 고정한 후에만 정답 비용추계서를 확인한다. 다음을 분리해 비교한다.

- 비용유발 요인 탐지 오류
- 라우팅 오류
- 산식 선택 오류
- 변수·단가 선택 오류
- 시행연도·추계기간 오류
- 반올림·단위 변환 오류

오차율은 금액이 0이 아닌 경우 다음과 같이 기록한다.

```text
절대오차율 = |최초 추계액 - 정답| / |정답| × 100
```

최초 결과를 보강 결과로 덮어쓰지 않는다.

### 7단계: 재사용 가능한 형태로 보강

실패 원인에 따라 한 가지만 보강한다.

- 라우팅 문제: `route_tree.py`의 분류나 말단 추가
- 산식 문제: 반복 가능한 고정 산식과 검증 규칙 추가
- 변수 문제: 출처·단위·적용조건을 포함한 근거 행 추가
- 선택 문제: 잘못된 후보를 거부하는 조건과 테스트 추가

정답의 최종 합계는 저장하지 않는다. 정답에서 확인한 변수를 개발 근거로 저장할 수는 있지만
`development_review`임을 명시하고, 다른 의안에 사용할 때 다시 적용 가능성을 판단해야 한다.

### 8단계: 재구축과 회귀 테스트

```bash
python3 -m backend.erce.scripts.build_variable_table
python3 -m unittest discover -s backend/erce/tests -p 'test_*.py' -v
```

기존 테스트가 모두 통과하고, 새 실패를 재현하는 테스트가 추가되어야 작업이 끝난다.

## 6. 완료 기준

의안 한 건은 다음 조건을 모두 충족해야 완료로 본다.

- 정답 확인 전 최초 결과가 문서에 남아 있다.
- 라우팅이 하나의 등록된 산식 말단에 도달한다.
- 모든 사용 변수에 값, 단위, 출처, 적용 이유가 있다.
- 부적절한 후보를 제외한 이유가 기록되어 있다.
- 출처 없는 숫자와 정답 합계 하드코딩이 없다.
- 최초 결과와 보강 결과가 분리되어 있다.
- 새 테스트를 포함한 ERCE 전체 테스트가 통과한다.

## 7. Git 작업 규칙

브랜치는 담당 비용유형별로 만든다.

```text
feature/erce-{비용유형}-{이름}
```

예시: `feature/erce-transfer-minsu`

- 의안 한 건당 가급적 커밋 한 개를 사용한다.
- ERCE와 관계없는 파일을 함께 커밋하지 않는다.
- 로컬 SQLite, PDF 원본, 생성 결과물은 커밋하지 않는다.
- PR에는 아래 표를 작성한다.

| 의안번호 | 비용유형 | 최초 추계액 | 정답 | 오차율 | 실패 원인 | 보강 내용 |
|---|---|---:|---:|---:|---|---|

## 8. 팀원에게 전달할 작업 요청문

```text
ERCE에서 [담당 비용유형] 개발용 의안 5건을 한 건씩 처리해 주세요.

반드시 docs/erce/ERCE_TEAM_WORK_GUIDE.md의 순서를 따라 주세요.
정답 비용추계서를 보기 전에 법안 원문만으로 라우팅·산식·변수 선택과 최초 결과를 기록하고,
그 후 정답과 비교해 실패 원인을 분류합니다. 보강은 다른 의안에도 재사용할 수 있는
라우팅·산식·근거 데이터·거부 조건으로만 반영합니다.

검증셋 사용, 출처 없는 숫자 생성, 정답 합계 하드코딩, 최초 결과 덮어쓰기는 금지합니다.
의안별 사례 문서와 테스트를 남기고 비용유형별 브랜치에서 PR을 올려 주세요.
```
