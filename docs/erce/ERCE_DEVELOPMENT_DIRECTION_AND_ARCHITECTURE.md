# ERCE 개발 방향과 목표 구조

작성일: 2026-10-03

목적: 기존 구현을 활용하면서 산식·변수·가정을 축적하고, 새로운 의안에도 재사용할 수 있도록 개발 기준을 정리한다.

## 1. 우리가 만들려는 것

ERCE는 법안 원문을 분석해 비용유발 항목을 찾고, 검토된 산식과 출처 있는 변수값을 사용해 **사람이 검토·수정할 수 있는 합리적인 비용추계 초안**을 만드는 시스템이다.

좋은 추계의 기준은 다음과 같다.

- 비용이 발생하는 항목과 부담 주체를 적절하게 식별한다.
- 현행 제도와 개정 후 제도를 구별해 추가 지출·수입 변화를 계산한다.
- 계산 대상에 맞는 산식과 변수를 사용한다.
- 법안에 명시된 사실, 공식 기준, 선례에서 빌린 가정, 사용자 선택을 구분한다.
- 계산 과정과 출처를 확인할 수 있고, 가정을 바꾸면 영향을 받는 금액을 다시 계산할 수 있다.
- 미추계 범위를 남기고, 계산한 일부 금액을 전체 법안 비용으로 표시하지 않는다.

자료가 없는 대상인원이나 미래 집행방식을 항상 확정할 수는 없다. 이때는 적용 가능한 가정 후보와 그 근거를 제시하는 것도 유효한 결과다. 다만 일반적인 유형에서 반복되는 산식과 변수는 점차 자동으로 채울 수 있어야 한다.

## 2. 현재까지 구현된 것과 부족한 것

**기존 작업이 없는 상태가 아니다.** 고정 산식, 변수 근거 DB, 일부 유형의 하위 계산은 이미 구현되어 있다. 다음 개발은 이 기능들을 공통 구조로 연결하는 작업이다.

| 영역 | 현재 상태 | 다음 보강 |
|---|---|---|
| 의안 분석 | PDF에서 조문·비용유발 항목·잠정 라우팅·명시 변수를 구조화하고 인용을 확인 | 방법 선례 검색 후 AI가 판단을 다시 검토하는 단계 연결 |
| 라우팅·산식 | 비용 성격별 트리와 등록 산식 선택 구현 | 적용 조건을 명확히 하고 기존 산식 재사용을 우선 |
| 변수 근거 | 값·단위·출처·시점·범위·재사용 제한 저장 | 변수의 의미와 유형별로 다른 검증 항목을 공통 정의로 정리 |
| 변수 선택 | 선택한 DB ID를 조회하고 적용 범위·시점 등을 검증 | 후보 검색·의미 판단·선택 이유 기록을 일관된 흐름으로 연결 |
| 하위 계산 | 장학금 대상인원 전망·지원상한 계산, 일부 대출 재원·이자 계산 등에 구현 | 필요한 변수를 등록된 하위 산식으로 계산하는 공통 기능 |
| 방법 선례 | 별도 저장·키워드 후보 검색·선택 조건 검증 구현 | 관련 선례 확대 및 검색 성능 평가 |
| 계산·초안 | Python 계산과 방법·변수 출처를 포함하는 초안 생성 연결 | 하위 계산까지 이어지는 출처·가정 추적 |
| 웹·AI | 웹 계산 API가 선택된 DB 근거를 수용 | GPT의 자동 재판정·근거 ID 선택, 채팅 UI의 선택 흐름 연결 |
| 검증 | 첫 실행 기록과 사후 보강 결과를 구분 | 의안 계열별 격리, DB 버전 고정, 독립 재사용 성능 평가 |

현재 로컬 DB 확인값은 변수 근거 366행, 공식 월 기본봉급 516행, 방법 선례 4행, 방법–변수 연결 1행이다. 이는 **PDF 수나 완성된 추계 유형 수가 아니라 저장 레코드 수**다.

방법 선례 4건은 기본계획 용역, 입학금 폐지 보전, 단체 운영경비 지원, 학생대출 이자면제다. 마지막 세 사례는 방법을 등록한 단계이며, 부족한 숫자 근거와 하위 계산을 모두 완성한 것은 아니다. 특히 기존 대출 재원 계산과 새 학생대출 이자면제 계산을 같은 구현으로 취급하지 않는다.

## 3. 이 방향을 선택하는 근거

### 3.1 정책 계산 엔진: 변수와 하위 산식을 연결한다

OpenFisca는 입력 변수와 산식으로 계산하는 변수를 구분한다. 산식은 특정 기간의 변수값을 계산하며 다른 변수에 의존할 수 있다. 기준값은 별도 파라미터로 관리한다. PolicyEngine도 정책 규칙과 대상 데이터에 기반해 현행·개정 제도를 계산하는 구조를 제공한다. [OpenFisca 변수·산식](https://openfisca.org/doc/key-concepts/variables.html), [기준값 관리](https://openfisca.org/doc/key-concepts/parameters.html), [PolicyEngine 정책 변경](https://policyengine.github.io/policyengine.py/reforms.html)

ERCE에 적용할 점은 **대상인원이나 연간 단가도 계산 결과일 수 있다는 것**이다. 최종 금액 산식만 저장하지 않고, 그 입력 변수를 구하는 산식까지 재사용한다. 이들 엔진은 최신 논문이 아니라 운영 중인 정책 계산 구조의 참고 사례다. 전체 프레임워크를 도입할 필요는 없으며, OpenFisca의 누락값 기본값 반환 방식도 ERCE의 미확정 변수 처리에 그대로 적용하지 않는다.

### 3.2 금융 추론 연구: 설명과 입력 정의가 있는 함수를 재사용한다

FinanceReasoning(ACL 2025)은 설명·매개변수 정의·구현을 갖춘 Python 금융 함수 3,133개를 구성했다. 해당 실험에서는 관련 함수를 검색하는 방식이 일반 문서 검색보다 유리한 결과를 보였다. [논문](https://aclanthology.org/2025.acl-long.766/)

ERCE의 산식도 표현식뿐 아니라 **무엇을 계산하는지, 어떤 조건에 적용하는지, 각 입력의 의미가 무엇인지**를 함께 관리해야 한다. 금융 질의응답 실험의 결과가 국회 비용추계 정확도를 보장하는 것은 아니므로 우리 의안으로 효과를 검증한다.

### 3.3 경험 축적 연구: 성공 방법과 잘못 적용한 조건을 함께 저장한다

FinAcumen의 2026-09-21 개정본은 성공한 해결 전략과 실패에서 얻은 주의사항을 구분해 저장하고, 관련성이 충분한 경험만 활용한다. 평가할 때는 경험 저장소를 고정해 평가 정답이 다음 문제에 흘러들지 않도록 한다. [논문](https://arxiv.org/abs/2606.17642)

ERCE에는 산식·값뿐 아니라 **적용하면 안 되는 조건과 실제 실패 이유**도 축적한다. 예를 들어 학생금리와 조달금리를 혼동한 사례를 관련 방법에 연결한다. 이 연구는 사전공개 논문이며, 모델의 자기판정만으로 새로운 공식 근거를 승인하는 방식을 채택한다는 의미는 아니다.

### 3.4 기준값과 정답도 버전·전제를 보존한다

PolicyBench는 2026-09-22 기준값 감사에서 참조 엔진 결함과 프롬프트에 없는 입력 등의 문제를 확인했다. 공식 발표값이 있는데도 과거 기준값의 물가 연장에 의존하는 문제도 다뤘다. [감사 기록](https://policybench.org/notes/2026-09-22-reference-audit)

ERCE에서도 공식 자료의 발표일·적용연도·개정 이력과 정답 추계서의 가정·추계 범위를 보존한다. 정답과 차이가 나면 먼저 우리 계산을 점검하되, 정답의 반올림이나 특수 가정을 분리해서 설명한다.

추계 가정과 민감도 분석의 근거로는 GAO의 비용추계 지침도 참고한다. 이는 2020년 지침이며 최신 AI 연구와 구분한다. [GAO 비용추계 지침](https://www.gao.gov/products/gao-20-195g)

## 4. 목표 시스템 구조

아래는 **앞으로 연결할 목표 구조**다. 모든 단계가 현재 자동화되어 있다는 뜻은 아니다.

```text
의안 PDF
   ↓
AI: 실제 변경 내용·비용유발 항목·부담 주체·명시 변수 추출
   ↓
방법 선례 검색 → AI: 현행 제도와 신규 비용, 적용 조건 검토
   ↓
항목별 라우팅 → 등록된 산식 선택
   ↓
필요 변수 해결
   ├─ 직접 사용 가능한 명시값·실적·공식 기준 조회
   ├─ 등록된 하위 산식으로 계산 가능한지 확인
   │    └─ 그 산식이 요구하는 변수·근거를 다시 조회
   └─ 부족하면 적합한 선례 가정 후보 또는 사용자 입력 요청
   ↓
단위·기간·대상집단·중복·가정 일관성 확인
   ↓
Python: 하위 변수 → 항목별 금액 → 연도별 순증액 계산
   ↓
출처·가정·미추계 범위가 표시된 초안
```

### 4.1 라우팅 트리와 계산 연결은 역할이 다르다

라우팅 트리는 비용유형과 사용할 산식을 찾는 분류 구조다. 계산 연결은 어떤 변수로 다른 변수를 구하는지 나타낸다. 같은 하위 산식은 여러 라우팅에서 재사용할 수 있다.

예를 들어 특정 급여 유형에서는 다음 구조를 사용할 수 있다.

```text
추가 재정소요 = 개정 후 지원액 − 현행 지원액

지원액 = 대상자 수 × 연간 지원액 × 정부 부담률
대상자 수 = 대상인구 × 자격 충족률 × 자격집단의 신청률
연간 지원액 = 월 지원액 × 지원개월
```

이 예시는 모든 지원사업에 고정 적용하는 공식이 아니다. 비율의 분모가 서로 맞아야 하며, 이미 신청자를 집계한 수에 신청률을 다시 곱하면 안 된다. 정확한 대상자 실적이 있다면 대상인구 비율 계산을 생략할 수 있다.

하나의 의안에서 인건비·운영비·시설비가 함께 발생할 수 있으므로 의안 전체를 하나의 말단 산식에 넣지 않는다. 비용항목별로 계산하고 포함관계를 확인해 합산한다. 정책 목적 태그와 비용 성격 분류도 별도로 유지한다.

### 4.2 AI·코드·사용자의 역할

| 주체 | 담당 역할 |
|---|---|
| AI | 조문 해석, 비용항목 구분, 방법·산식 후보의 적용 판단, 변수 후보의 의미 비교, 선택·제외 이유 설명 |
| 코드 | 등록 산식 실행, 근거 ID 조회, 시점·형식·단위 등 검증, 계산 순서 결정, 중복·누락 상태와 출처 기록 |
| 사용자 | 자료로 확정할 수 없는 정책 실시·규모·적용 가정 확인 또는 직접 입력 |

개발 중에는 에이전트가 AI 역할을 하고, 서비스에서는 API 모델이 같은 입력·출력 계약을 사용하도록 연결한다. 새로운 산식은 검토·등록·테스트 후 사용하며, 실행 중 AI가 만든 임의 코드를 계산기로 바로 실행하지 않는다.

## 5. 무엇을 어떤 단위로 쌓을 것인가

아래는 기존 필드를 활용해 점진적으로 정리할 **논리적 데이터 구조**다. 모든 항목을 새 테이블로 즉시 만들 필요는 없다.

| 축적 대상 | 저장할 핵심 내용 | 예시 |
|---|---|---|
| 방법 선례 | 적용 조건, 기존 비용 확인, 부담 주체, 가정, 제외 조건, 연결 산식 | 입학금 폐지 시 정부 보전을 가정한 추계 방법 |
| 산식 | ID·버전, 입력·출력 변수, 적용 조건, 실행 함수, 기간·반올림 규칙 | 연간 면제이자 = 대출잔액 × 학생금리 |
| 변수 정의 | 정확한 의미, 단위, 대상 주체, 기간, 집계 방식, 비율의 분모, 허용 근거 종류 | 재학생 중 신규 이자면제 대상자 수 |
| 변수 근거 | 값·시계열, 출처·페이지·표, 공개일, 적용연도, 지역·집단·규모, 실적/전망/가정 구분 | 특정 연도의 등록금 대출 평균잔액 |
| 변수 산출법 | 출력 변수, 하위 입력, 계산 함수, 적용 조건·대리 가정 | 대상인구와 조건별 비율로 대상자 수 산출 |
| 실행 기록 | 선택·제외한 후보, 이유, 적용 가정, 각 계산 결과, 미해결 변수, 데이터·산식 버전 | 같은 단가 후보 중 부처·규모 차이로 하나 제외 |

운영 원칙:

1. **같은 산식이면 재사용한다.** 새로운 이름의 의안이라고 동일 계산 함수를 추가하지 않는다. 적용 조건이나 변수 역할이 다르면 별도 방법·정의로 구분한다.
2. **공식 파라미터와 사례 가정을 구분한다.** 공무원 월 기본봉급, 공식 통계와 특정 추계서의 인원 가정은 같은 성격의 값이 아니다.
3. **적용 가능성을 먼저 확인한 뒤 출처 우선순위를 적용한다.** 명시된 지원한도는 실제 지급액이 아니며, 최신 공식 자료라도 다른 집단의 값이면 바로 사용할 수 없다.
4. **비교 단가에는 규모·기능을 남긴다.** 총사업비와 대상 수가 있다고 무조건 나눠 범용 단가로 만들지 않는다. 고정비·규모 효과·업무 내용 차이를 확인한다.
5. **갱신해도 과거값을 보존한다.** 발표일, 유효기간, 가격 기준연도, 자료 버전을 따로 기록한다. 미래 값의 동결·물가 보정·인구 전망은 계산 가정으로 표시한다.
6. **대상 의안 전용 값은 전용으로 남긴다.** 재사용 가능한 것은 숫자 자체인지, 산출 방법인지, 적용 조건인지 각각 판단한다.
7. **독립적인 가정을 섞지 않는다.** 서로 다른 집행 시나리오의 대상인원·단가·지원율을 조합하거나 대안 시나리오들을 합산하지 않는다.

### 변수 해결 순서

1. 현재 변수의 대상·단위·기간·의미를 확인한다.
2. 직접 사용할 수 있는 명시값·실적·공식 기준을 찾는다.
3. 직접 값이 부족하면 등록된 하위 산식과 그 입력 근거로 구할 수 있는지 확인한다.
4. 적용 가능한 비교 사례나 대리 가정이 있으면 한계와 함께 후보로 제시한다.
5. 여러 후보가 모두 합리적이면 영향이 큰 가정을 사용자에게 확인하거나 별도 시나리오로 계산한다.
6. 끝내 해결하지 못한 변수와 영향을 받는 비용항목을 명시한다.

하위 계산에는 순환 의존 탐지와 탐색 한도를 두고, 해결하지 못한 값을 0으로 채우지 않는다. 가정을 사용해 계산한 파생값에도 가정이라는 성격과 원자료 출처가 이어져야 한다.

사용자에게는 원시 변수 전체를 한꺼번에 묻지 않는다. 먼저 DB 조회와 하위 계산을 수행하고, 남은 선택 중 결과에 영향을 크게 주는 가정부터 짧게 확인한다. 범위를 제시할 때도 임의의 ±비율을 붙이지 않고 근거 있는 대안값을 사용한다.

## 6. 한 의안씩 보강하는 작업 방식

### 6.1 정답을 보기 전

1. 개발 목록에서 다음 의안을 고른다. 따로 격리한 평가셋은 개발용으로 사용하지 않는다.
2. 원문만 읽고 비용항목·부담 주체·순증 범위·방법·산식 후보를 정한다.
3. 자기 의안의 정답, 정답에서 추출한 자료, 평가에서 제외할 유사 의안, 기준일 이후 자료를 검색에서 제외한다.
4. 기존 산식·변수 근거·산출법으로 실행하고 부족한 부분을 기록한다.
5. 입력·선택 이유·근거 ID·결과를 첫 실행 파일에 고정한다.

### 6.2 정답을 확인한 뒤

실패 지점을 먼저 나누고 그 부분을 보강한다.

| 차이의 원인 | 보강할 대상 |
|---|---|
| 비용항목·부담 주체를 놓침 | 방법 선례, 현행 비용 확인 기준, AI 판단 사례 |
| 산식이 없거나 잘못 선택됨 | 기존 산식의 적용 조건 또는 검토된 신규 산식 |
| 변수 근거 자체가 부족함 | 공식 자료 조사·적재 또는 재사용 범위를 명시한 선례 근거 |
| 적절한 근거가 있는데 검색되지 않음 | 변수 의미·검색어·필터·연결 정보 |
| 후보에 있었는데 잘못 선택함 | 대상·단위·시점 비교와 후보 제외 조건 |
| 최종 변수값은 없지만 하위 자료가 있음 | 변수 산출법과 하위 산식 연결 |
| 일부 금액만 맞거나 중복됨 | 포함 범위·현행 대비 차액·기간·집계 방식 |

정답의 숫자를 역산해서 빈 변수를 채우지 않는다. 정답에서 새 근거를 얻었다면 출처와 정답 유래 사실을 남기고, 해당 의안의 첫 실행 입력과 분리한다. 정답에 나타난 의안 전용 가정은 범용 공식값으로 승격하지 않는다.

### 6.3 보강을 마쳤다고 보고하는 기준

- 산식이 등록되고 실제 실행 경로에 연결되어 있다.
- 각 필수 변수의 확보·파생 계산·미해결 상태가 명확하다.
- 근거가 필요한 값에 출처와 적용 범위가 있다.
- 확인하지 못한 가정과 미추계 항목을 숨기지 않는다.
- 같은 의안의 회귀 실행에서 보강한 기능이 작동한다.
- **재사용 성능은 정답을 안 본 다른 의안에서 별도로 확인한다.**

하나의 의안 보강 결과는 다음 형식으로 간단히 남긴다.

```text
의안번호 / 비용유형 / 첫 실행 기준일
비용항목: 정답 대비 발견·누락
산식: 선택 결과와 정답 차이
변수: 명시값·공식값·파생값·가정값·미해결 개수
미해결 원인: 근거 부족 / 검색 누락 / 선택 실패 / 하위 계산 미연결
금액: 같은 추계 범위의 연도별 비교와 오차
보강: 산식 ID·변수 근거 ID·산출법·주의사항
재사용 제한 / 남은 작업 / 다음 독립 확인 대상
```

## 7. 개발 순서와 완료 조건

### 1단계: 기존 하위 계산 한 종류를 공통 구조로 연결

첫 대상은 이미 구현된 장학금 대상인원 전망을 권장한다. 입력·출력 변수와 연도·단위 검사가 존재해, 새 계산을 만드는 작업과 공통화 작업을 분리해서 검증하기 좋다.

- 기존 계산 함수는 유지하고 입력·출력·적용 조건을 등록한다.
- 최종 산식에 `recipient_count`가 없으면 해당 산출법을 후보로 찾는다.
- 적용 조건과 입력 근거가 충족됐을 때 기존 함수를 실행한다.
- 대상자 수가 직접 주어지면 기존 우선순위대로 사용한다.
- 적용한 성장 가정과 원자료가 최종 변수·초안에 전달되게 한다.

완료 조건: 기존 결과가 유지되고, 필요한 하위 입력이 없거나 조건이 다르면 정확한 이유로 보류한다. 새로운 대상에 기존 의안의 인원수를 복사하지 않는다.

### 2단계: 재사용할 변수 정의와 검색 조건 정리

인원, 단가, 지원율, 기간, 현행 비용 등 자주 쓰는 변수부터 의미·단위·기간·대상 범위를 정리한다. 기존 DB 행을 가능한 범위에서 이 정의와 연결하고, 누락된 출처만 필요한 문서로 돌아가 보강한다.

완료 조건: 적절한 후보를 찾지 못한 것과 DB에 해당 근거가 없는 것을 구별해 기록할 수 있다. 모든 PDF를 처음부터 다시 처리하는 것을 선행 조건으로 두지 않는다.

### 3단계: 같은 방식으로 하위 계산 확대

대출 잔액×금리, 월 단가×개월, 단체 수×운영단가 등 반복되는 계산을 등록한다. 유형별 예외와 조건은 유지하면서 공통 실행 경로에 연결한다.

완료 조건: 새 산식 또는 산출법을 추가할 때마다 주 엔진의 의안별 조건문을 늘릴 필요가 줄어든다. 조건이 다른 유형은 무리하게 하나의 산식으로 합치지 않는다.

### 4단계: AI 재판정과 채팅 흐름 연결

방법 후보와 변수 후보를 API 모델에 전달해 적용 여부·선택 ID·제외 이유를 받는다. 코드로 검증하고, 불확실한 가정만 채팅에서 확인한다. 개발 에이전트와 API 모델이 같은 데이터 계약을 사용한다.

완료 조건: 사용자가 확인한 가정, DB 근거, 하위 계산 결과가 초안까지 유지된다. 서비스 재시작이나 재계산 후에도 같은 입력·버전의 결과를 재현할 수 있다.

### 5단계: 새 의안으로 효과를 확인한 뒤 확대

새 의안군에서 보강 전후의 비용항목 탐지·산식 선택·변수 해결·금액 오차를 비교한다. 검색 때문에 후보를 놓치는 비중이 높을 때 키워드·벡터 혼합 검색을 실험한다.

완료 조건: 추가한 자료가 다른 의안의 성능을 개선하고 기존 유형을 악화시키지 않는지 확인한다. 저장 건수 증가만을 성과로 삼지 않는다.

## 8. 평가와 운영 기준

- 개발 중 보강용 사례, 같은 의안의 회귀 검증, 독립 평가셋을 구분한다.
- 평가에서는 산식·DB·방법 선례·모델·프롬프트 버전과 자료 기준일을 고정한다. 평가 도중 얻은 정답을 DB에 추가하지 않는다.
- 재발의·유사 의안과 같은 원자료를 공유하는 사례는 계열로 묶어 누출을 점검한다. 현재 동일 계열 전체의 자동 구축은 미완성이므로 목록을 명시적으로 관리한다.
- 비용항목 발견률, 산식 선택, 적절한 후보 검색, 후보 선택, 필수 변수 해결률을 구분한다.
- 금액 오차는 정답과 같은 항목·기간·부담 주체·일부추계 범위에서 비교한다. 정답이 0이거나 매우 작을 때는 단순 백분율 오차만 사용하지 않는다.
- 자동 계산된 항목의 오차와 전체 항목 중 계산 가능한 비중을 함께 보고한다. 쉬운 항목만 계산해서 평균 오차가 낮아진 상황을 구별한다.
- 기존 150개 테스트 통과와 2217718 기본계획의 연결 검증은 기능 동작의 근거다. 새로운 의안의 비용 정확도를 입증한 수치는 아니다.

벡터 검색은 후보 회수율을 높이는 선택지다. 관계형 DB의 명시적인 산식·변수·근거 연결부터 활용하고, 후보 검색 평가에서 필요성이 확인되면 추가한다. 계산 의존관계를 사용한다는 이유만으로 별도 그래프 DB나 GraphRAG가 필요한 것은 아니다.

기존 SQLite 구조와 공유 스냅샷을 유지하면서 논리적 ID·관계·시점 필드를 정리한다. 추후 PostgreSQL/Supabase 이전 시에도 이 정의를 보존한다. 이 문서의 목표 구조 중 구현되지 않은 부분은 구현·검증을 마친 뒤 상태를 갱신한다.
