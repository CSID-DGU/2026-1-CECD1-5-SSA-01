## 1. Upstage 모델(solar-pro2 / solar-pro3)의 문제점 — 실측 기준 정리

### 1-1. 사건 탐지(detect) 비결정성 — temperature=0에서도 발생

같은 의안, 같은 코드, `refresh=True`로 매번 새로 호출해도 **탐지되는 사건 집합 자체가 달라짐**.

- 2214559: 3회 반복 호출 중 2회는 "친환경농어업발전위원회" 정상 탐지, 1회는 누락.
- 2213320: "국가인공지능데이터센터진흥위원회"가 3/3 전부 누락된 적도 있음(인식률 자체가 낮은 케이스).
- 2214559(다른 호출): 원문에 존재하지 않는 "한부모가족지원센터"를 **환각으로 지어냄** — 텍스트 직접 대조로 원문에 없음을 확인.

**결론**: temperature=0으로 불러도 Solar 계열은 완전한 결정론을 보장 못 함. 회귀 테스트가 캐시(고정 응답) 기반이라 이 비결정성을 그동안 검증한 적이 없었다는 것도 이번에 확인됨(회귀 캐시 라이브 재실행 시 7건 중 2건이 이전 통과 상태에서 이탈).

### 1-2. confidence 자기평가가 정확도와 무관 (미보정)

- 2125736(공무원보수위원회): 완전히 무관한 도메인(ESG경영위원회) 선례를 골라놓고 confidence=0.90.
- 같은 세션의 정상 케이스(2126636, 2213937 등)도 동일하게 confidence=0.90.
- 즉 confidence 값이 "그럴듯한 문장을 만들었는지"를 반영할 뿐, **선례가 실제로 맞았는지와 상관없음.**
- 웹 리서치로 확인: 2026년 다수 논문이 "verbalized confidence는 원래 과신되며 보정 없이 쓰면 안 된다"를 공통 결론으로 제시(참고: "Know When You're Wrong", "How Reliable are Confidence Estimators..." 등).
- **대응**: `adversarial_verify.py` — 별도 LLM 반박 호출로 선례 선택을 재검증. 227% 오차 사례를 정확히 잡아 needs_user_input으로 되돌리는 데 성공(실측 확인).

### 1-3. JSON 생성 문법 오류 (재시도 로직 누락 — 코드 버그, 모델 문제 아님)

- 증상: `[upstage 오류] Expecting ',' delimiter` — 사건이 많은 의안에서 간헐적(비결정적) 발생, 심하면 트레이스백까지 노출.
- 최초 가설(오진): max_tokens 미설정 → 응답 잘림. `finish_reason`을 직접 캡처해 확인한 결과 **'stop'(안 잘림)이었음 → 가설 기각.**
- 진짜 원인: `gemini_json()`의 재시도 루프(`for attempt in range(3)`)가 HTTP 429/5xx는 재시도하면서 **`json.JSONDecodeError`는 재시도 없이 즉시 포기**하도록 짜여 있었음(`backend/analyzer_v2.py`).
- **수정**: `json.JSONDecodeError` 전용 except 분기를 추가해 HTTP 5xx와 동일하게 최대 2회 재시도. 수정 후 동일 의안 3회 연속 크래시 없이 완료 확인.
- 교훈: "모델이 가끔 문법을 실수한다" 자체는 흔한 LLM 특성이고, 문제는 **그걸 재시도로 완충하는 인프라가 없었던 것**.

### 1-4. Additionality(신규 vs 현행유지) 오판 — 모델 버전 교체로도 미해결

같은 방향으로 반복되는 편향: **진짜 신규 사업을 "이미 있던 것"으로 잘못 판단**.

| 의안 | 실제 | 판정 |
|---|---|---|
| 2216417 | 비상임위원 신규 회의수당(2,685백만) | staffing으로 오분류 |
| 2215935 | 시민고충처리위 신규 설치·운영 | 인건비로 오분류, 총액준용 구조 놓침 |
| 2126685 | 전문위·사무처 신설(4,929백만) | "현행유지"로 잘못 제외 |
| **2126677** | **외국인근로자 기숙사 지원사업(46,000백만, 신규)** | **"현행 유지 사건" 또는 "선언적 규정"으로 제외(재실행마다 다른 핑계로 틀림)** |

- 2126677을 `solar-pro2`와 `solar-pro3` **양쪽 모두**로 라이브 재실행 → **둘 다 동일하게 오판**. 모델 버전 문제가 아니라 **`detect.py`의 additionality 판정 프롬프트 자체의 구조적 결함**으로 확인.
- 위치: 오판 자체는 `detect.py`(LLM 호출)에서 발생, 그 값을 그대로 신뢰해 배제하는 코드는 `backend/estimator_v2/gates.py:137` (`if event.additionality == "existing_or_unchanged": ... EXCLUDED`).
- **미해결. 다음 세션 최우선 과제.** 프롬프트를 넓게 고치면 과거에 3/7 회귀를 깨먹은 전적이 있어(위원회 관련 원칙을 넓혔다가 판사·공무원 조직까지 오분류됨) — 좁고 검증 가능한 수정이 필요.

### 1-5. 재랭킹이 최상위 원본 후보를 탈락시킴

- 지원금(2126650, 군복무크레딧): 원본 임베딩 검색 1위는 "2216470 군 복무기간에 대한 가입기간 추가 산입"(유사도 0.606, 이름·산식 구조 정답지와 사실상 동일)였지만, **row.selected_candidates(재랭킹 이후)에는 아예 빠져있었음** — 대신 유사도 0.547짜리 무관한 선례(육아휴직)가 최종 후보로 남음.
- **대응**: `subsidy_formula_presenter.py`가 표시 직전 원본 `search_cost_candidates`를 재호출(임베딩 캐시 재사용, 추가 LLM 비용 없음)해 raw 최상위 후보를 우선하도록 시도. 코드는 정상 동작했으나, **그 원본 검색 자체도 매 호출마다 사건의 quotes(조문 인용) 내용이 달라져 검색 결과가 흔들림** — 결국 1-1의 비결정성으로 귀결.

## 2. 오늘 만든 격리(opt-in) 모듈 — 전부 회귀 안전성 확인됨

| 모듈 | 역할 | 검증 결과 |
|---|---|---|

| `committee_bridge.py` | 위원회 항목은 v2 결과와 무관하게 v5(정규식, 안전) 산식으로 강제 대체 | 산식 정확 제시 확인, 숫자 확정 안 함 |

| `subsidy_auto_scope.py` | `_AUTO_TYPES`에 없는 지원금을 opt-in으로 자동계산 범위에 포함 | 검색 시도는 가능해짐, 틀린 확신 없음(안전) |
| `subsidy_formula_presenter.py` | 값이 빈 최유사 선례라도 산식·변수명은 표시(새 LLM 호출 없음) | 표시 기능 자체는 동작, 입력 비결정성으로 최적 후보 선택은 불안정 |
| `analyzer_v2.py` JSON 재시도 | `JSONDecodeError`를 HTTP 5xx처럼 재시도 | 크래시 재현 안 됨 확인 |
