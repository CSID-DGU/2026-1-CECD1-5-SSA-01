> 어디서 틀렸는지, 그리고 그 원인이 **"DB에 적절한 산식·값이 있었는데 못 고른 것(🔧)"**인지
> **"DB에 진짜 없는 것(⬜ HITL)"**인지를 항목 단위로 기록한다.
> 엔진: `backend.estimator_v2` (v2.34.0) / LLM: `upstage:solar-pro2`

## 채점 분류 기호
- ✅ DB에 적정 산식·값 있음 + 시스템이 제대로 고름
- 🔧 DB에 있음 + **잘못 고름/못 만듦** → 우리가 고칠 지점 (선택·분류·게이트)
- ⬜ DB에 진짜 없음 → HITL 정당 (선택 문제 아님)

## C. 3케이스 종합 — 실패의 뿌리 (전부 상류: detect/gate)

| 의안 | 공식 실제 방법 | 시스템 실패 | 유형 | 소유 파일 |
|---|---|---|---|---|
| 2216417 비상임위원 | 회의참석수당 | 보수(staffing)로 오분류 | cost_mechanism | detect.py, organization.py |
| 2215935 시민고충처리위 | 운영예산 총액준용 ×N | 인건비로 오분류, ×N 미탐지 | cost_mechanism | detect.py, organization.py |
| 2126685 전문위·사무처 | 최저임금위 크로스도메인 준용 | 신설을 현행유지로 제외 | additionality + 크로스도메인 준용 부재 | detect.py, gates.py, retrieval.py |

**핵심 결론:**
1. 처음 의심한 "선례 랭킹"은 표면. 진짜 병목은 **detect/gate의 의미 판단**(cost_mechanism·additionality).
2. **NABO 정답지가 크로스도메인 유사준용을 실제로 함**(2126685 최임위 준용). 시스템의 "동일 family + 완결 단일선례" 엄격 정책이 NABO보다 보수적 → 리즈너블 준용 티어 필요(Q2).

## D. 개선 대상 파일 (우선순위)
1. **`backend/estimator_v2/detect.py`** — event_type·cost_mechanism·additionality 최초 배정(LLM 프롬프트). 3케이스 공통 뿌리.
2. **`backend/estimator_v2/organization.py`** — 조직 이벤트를 staffing vs committee(회의수당) vs 운영예산준용으로 라우팅. `_is_legislative_committee_organization_event` 확장.
3. **`backend/estimator_v2/gates.py`** — additionality→excluded 게이트(라인 137). 임의/의무 보정.
4. (Q2, 분류 이후) **`retrieval.py`**(family 필터 완화=기능유사 크로스도메인 허용) + **`selection.py`**(준용 신뢰도·review 플래그).

검증: `regression.py`(회귀 7건) + `test_estimator_v2.py`(106) + 항목별 채점표.
