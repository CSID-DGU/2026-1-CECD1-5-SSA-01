# 위원회 추계 DB 감사와 검색 구조 실험 계획

> 기준일: 2026-08-11  
> 범위: 위원회 비용추계 채널과 로컬 TAG/근거 데이터  
> 목적: 검색 알고리즘을 임의로 튜닝하기 전에, DB에 정답 근거가 실제로 있는지와 어느 단계에서 실패하는지를 분리해 측정한다.

## 결론

현재 병목은 데이터의 **양**이 아니라 다음 두 가지다.

1. 대상 조문과 공식 선례를 연결하는 `정답 선례 관계`가 저장돼 있지 않다.
2. 기존 항목 임베딩은 `비용항목명 + 카테고리`만 표현하므로, 법률 인용·준용 관계와 입법 이력 같은 식별 신호를 사용할 수 없다.

따라서 lexical·semantic·HyDE를 계속 바꿔 최고 점수를 고르는 방식으로는 일반화 성능을 입증할 수 없다. 먼저 공식 추계서를 이용해 `이 비용항목이 어떤 경로로 어떤 근거를 사용했는지`를 라벨링하고, 후보 검색과 최종 선택을 분리해 평가해야 한다.

현재 v5 엔진은 비용 **구조와 산식 경로**는 상당히 안정적으로 찾지만, 숫자에 필요한 선례를 자동 확정하는 비율은 매우 낮다. 네 개의 동결 5건 평가셋을 합치면 공식 비용사건 31개를 모두 탐지했고 호환 가능한 산식 경로도 31/31개였으며, 정확한 산식군은 29/31개였다. 반면 자동 숫자 초안은 1/31개뿐이었다. 즉 다음 개선 대상은 산식 템플릿 추가가 아니라 `근거 존재 판정 → 정답 선례 연결 → 피연산자 출처 검증`이다.

```text

  └─ committee_evidence_atoms
```

프로필에는 위원회명, 존속형태, 기능 분류, 소속기관, 총원, 유급위원 수, 하위위원회·사무조직 여부, 산식 시그니처가 저장된다. 근거 원자에는 `paid_members`, `annual_meetings`, `meeting_unit_price` 같은 피연산자와 출처·도출 방식·재사용 가능성이 저장된다.

즉 “DB에 숫자가 있다”와 “이 대상 조문에 그 숫자를 재사용해도 된다”는 전혀 다른 문제다. 현재 DB는 전자에는 강하지만 후자를 표현하는 관계 라벨이 부족하다.

## 현재 엔진이 실제로 사용하는 정보

### 일반 TAG 검색

`backend/scripts/precompute_tag_embeddings.py`는 각 항목을 다음 텍스트로만 임베딩한다.

```text
item_name + item_category
```

그러므로 다음 정보는 임베딩에 직접 포함되지 않는다.

- 대상 조문의 전체 법률 문맥
- 인용·준용한 법률명과 조문번호
- 동일 기관의 과거 운영 이력
- 공식 추계서가 명시한 실제 준용기관
- 산식 구성요소와 피연산자 완결성
- 재발의·경쟁법안·템플릿 계보

`tag_db.find_similar_items()`는 같은 family 안에서 이 임베딩 코사인 유사도를 사용한다. 구형 경로에서는 상위 후보들의 변수값을 역할별로 모두 모아 중앙값을 만들기도 하므로, 서로 다른 선례의 인원·횟수·단가가 합성될 수 있다.

### 위원회 v5

v5는 먼저 조문에서 위원회 사건과 구조를 추출한 뒤 구성요소 산식을 고른다. 단순 회의수당형의 실제 근거 실행은 v4/v3에 위임한다. v3는 임베딩으로 후보를 넓게 찾은 뒤 다음 신호를 사용해 재정렬한다.

- 위원회 기능
- 기관 동일성
- 프로필 구조
- 중앙·지방 소속 범위
- 대상 규모와의 양립성
- 산식 완결성
- 직접 출처 여부
- 의미 유사도

이 구조는 단순 유사도 검색보다 안전하지만, `기관 동일성`을 증명할 원문 인용관계나 정답 선례 링크가 DB에 없으면 결국 일반 위원회끼리 경쟁하게 된다.

## 현재 평가 결과의 정확한 의미

### 50건 수동 진단셋

`backend/generated/위원회_평가셋/test_result.md`의 50건은 매우 가치 있는 오류 분류 자료지만 완전한 end-to-end 성능시험은 아니다. 기록상 Claude가 조문을 직접 읽고 파서 역할을 대신하며 룰엔진을 한 건씩 검증했다. 따라서 이 자료는 다음에 적합하다.

- 정규식·규칙엔진 버그 발견
- 공식 추계 산식과 숨은 전제 분석
- 새로운 실패 아키타입 발견
- 선례준용·정부부처 제출자료 의존 비중 파악

반면 현재 LLM·검색기까지 포함한 자동 파이프라인 정확도로 인용하면 안 된다.

핵심은 “어떤 검색기가 더 좋은가”가 아니라 **대상 질의에 공식 선례를 식별할 정보가 있는가**다. 재발의·템플릿복붙·기관명 직접인용처럼 provenance가 드러난 사례만 현재 검색으로 안정적으로 접근할 수 있다.

## DB에 빠진 핵심 관계

기존 테이블을 폐기할 필요는 없다. 다음 관계층을 additive하게 추가해야 한다.

### 1. 대상 비용사건

```text
committee_cost_events
- event_key
- bill_id / article_ref / committee_name
- change_kind
- formula_family
- normalized_components
- cited_laws
- cited_articles
- named_institutions
- event_fingerprint
```

### 2. 공식 선례 연결 라벨

```text
committee_precedent_links
- target_event_key
- source_bill_id / source_item_key / source_profile_key
- link_type
  same_bill_history | same_institution_history | explicit_citation
  | named_institution | template_lineage | peer_average
  | generic_analogy | ministry_submission | external_actuals
- evidence_role
  whole_formula | whole_budget | paid_members | annual_meetings | unit_price
- source_quote
- label_status
  candidate | verified | rejected
- reviewer_notes
```

이 테이블이 있어야 “정답이 DB에 있었는데 검색이 못 찾음”과 “정답 근거가 DB에 없음”을 구분할 수 있다.

### 3. 법률 관계 그래프

```text
legal_reference_edges
- source_bill_id / source_article_ref
- relation_type: cites | applies_mutatis_mutandis | replaces | amends
- target_law_name / target_article_ref
- named_entity
- source_quote
```

`준용한다`, `제N조에도 불구하고`, 특정 기관의 기능을 수행한다 같은 관계를 먼저 따라간 뒤 그 관계와 호환되는 TAG 항목만 검색한다.

## 비교할 구조

모든 구조는 동일한 동결 평가셋과 동일한 시간 컷오프를 사용한다.

| 구조 | 후보 생성 | 최종 선택 | 용도 |
|---|---|---|---|
| A. 현재 baseline | 항목명+카테고리 임베딩 | 기존 v3 점수 | 비교 기준 |
| B. multi-field semantic | 항목명+산식+변수명+프로필 | 완결성 soft rerank | 정답 신호가 텍스트에 있는 사례 |
| C. template lineage | 조문 boilerplate 마스킹 후 fingerprint | 동일 계보·시간순 우선 | 템플릿복붙·경쟁법안 |
| D. citation/history graph | 인용·준용·동일기관·입법이력 edge | 관계 일치 후 산식·완결성 | 가장 우선할 구조 |
| E. route-specific late fusion | C/D와 semantic 후보를 합침 | route별 별도 점수와 게이트 | 최종 후보 구조 |

완결성은 후보를 검색 전에 제거하는 hard filter로 쓰지 않는다. 관계가 맞는 후보군 안에서 `공식 산식 피연산자가 얼마나 채워져 있는가`를 soft rerank 신호로 사용한다. 완결성만 높고 관계가 틀린 선례가 1위가 되는 것을 막기 위해 관계 경로가 먼저다.

## 공정한 실험 절차

### 1단계: 정답 선례 존재 여부부터 라벨링

공식 추계서마다 다음을 기록한다.

```text
공식 비용사건
→ 사용한 산식
→ 피연산자별 출처
→ 정확한 선례 기관·문서·항목
→ 현재 DB 존재 여부
→ evidence route
```

이 단계에서 결과를 다음 세 가지로 나눈다.

- `DB_PRESENT`: 정답 근거가 로컬 DB에 있음
- `EXTERNAL_ONLY`: 정부부처 제출자료·실기관 운영실적 등 외부에만 있음
- `UNIDENTIFIED`: 공식 문서에도 선례가 불특정하거나 현재 확인 불가

### 2단계: 후보 생성과 선택을 분리 평가

정답 근거가 DB에 있는 `DB_PRESENT`만 검색 평가에 사용한다.

- Candidate recall@10: 정답 선례가 후보 10개 안에 들어왔는가
- Precision@1: 들어온 정답을 최종 1위로 골랐는가
- MRR: 정답 순위가 평균적으로 얼마나 높은가

정답이 후보에 없으면 후보 생성 실패다. 후보에 있는데 다른 것을 고르면 재랭킹 실패다. 정답 자체가 DB에 없으면 검색 실패로 세면 안 된다.

### 3단계: 산식과 숫자를 별도 평가

- 비용사건 탐지 recall/precision
- exact formula family
- component coverage
- operand source completeness
- 자동 계산된 건의 20% 이내 비율
- 잘못된 자동 계산률(false-auto rate)
- 자동 계산 coverage

전체 건수 중 20% 이내 비율만 보면 HITL을 많이 하는 안전한 시스템과 무리하게 숫자를 만드는 시스템을 비교할 수 없다. `정밀도-커버리지`를 함께 보고해야 한다.

### 기존 실패 19건 회귀 결과

## 현재 최적 계층 구조

단일 유사도 점수 대신 다음 순서의 분리 경로를 채택한다.

```text
완결된 동일 법안·입법계보 패키지
  → 조문에 직접 명시된 변수
    → 해당 연도 공식 지침 단가
      → 같은 증거 주체의 검증된 운영실적
        → 부족한 변수만 Human-in-the-loop
```

- 완결 패키지 resolver는 기존 고유 46건 회귀를 유지했다.
- 9개 검색 구조 비교에서는 `routed_evidence`가 완결 선례 2/2,
  부분 근거 top-5 2/3으로 가장 좋았다.
- structural, domain, hybrid, late-fusion 점수를 더 섞어도 부분 근거
  성능은 개선되지 않았다.
- 구성요소 경로는 근거가 부족할 때 총액을 내지 않는다.

이 구조는 `backend/committee_hierarchical_evidence_engine.py`에 독립
실험 모듈로 구현했으며 TAG 파이프라인과 서버에는 연결하지 않았다.

## 연구 교차검증

현재 설계는 다음 1차 자료의 방향과 부합하지만, 논문 이름을 붙이는 것만으로
현재 데이터 결손이 해결되지는 않는다.

- [Microsoft GraphRAG](https://www.microsoft.com/en-us/research/publication/from-local-to-global-a-graph-rag-approach-to-query-focused-summarization/):
  엔티티와 관계를 텍스트 유사도와 별도로 구조화한다. 우리에게 필요한 것은
  전체 community summary가 아니라 법안·위원회·비교기관·지침 간 provenance edge다.
- [Corrective RAG](https://arxiv.org/abs/2401.15884): 검색 품질을 평가해
  경로를 전환한다. 우리의 `exact package / component prior / HITL` 라우팅과
  같은 계층적 안전장치로 해석할 수 있다.
- [RAGChecker](https://arxiv.org/abs/2408.08067): 검색과 생성 모듈을
  분리 진단한다. 본 평가도 `DB 존재 / 후보 회수 / 최종 선택 / 산식 / 숫자`를
  별도 지표로 유지한다.
- [SURE-RAG](https://arxiv.org/abs/2605.03534): 주제상 관련된 문서와
  답을 충분히 뒷받침하는 증거를 구분하고, 부족하면 abstain하는 selective
  retrieval 구조를 제안한다. 단순 위원회 유사도가 실행 근거가 될 수 없다는
  이번 실험 결과와 직접 맞닿아 있다.

이 기준을 통과한 뒤 숫자 20% 이내 비율과 커버리지를 올린다.

## 10건 파일럿 실행 결과

`backend/scripts/evaluate_committee_precedent_routes.py`로 첫 파일럿을 실행했다. 공식 추계서와 DB를 대조한 결과 10건 중 목표 시점 이전에 계산 가능한 독립 선례가 완결된 사례는 2건뿐이었고, 3건은 부분 근거, 5건은 외부자료 의존이었다.

관계 우선 후보 생성은 자동 가능한 두 사례의 정답을 모두 top-10과 최종 1위에 올렸다. 기존 문자검색 1위는 두 사례 모두 오답이었다. 자동 계산하면 안 되는 8건은 모두 중단했다.

```text
correct=10/10
actionable precision@1=2/2
candidate recall@10=2/2
safe abstention=8/8
```

단, 선택 게이트를 같은 10건에서 정했으며 양성 사례가 2건뿐이므로 일반화 수치로 인용하지 않는다. 이 결과는 관계 우선 구조의 실행 가능성과 안전한 중단을 확인한 개발 파일럿이다.

**#8. 2126661(이태원참사특조위) 재검증 — 픽스처 자체 버그 발견**

기존 픽스처를 다시 보니 `staff_headcount: 60`이 실제 매칭 엔티티명
("10ㆍ29이태원참사진상규명과재발방지를위한특별조사위원회")이 아니라 한
번도 안 쓰이는 별칭 키("조사위원회")에 들어있었다 — `_lookup_committee`가
더 긴 키를 우선 매칭해서 이 데이터는 죽은 코드였다. **키를 올바른
엔티티명으로 옮겨서 재실행**:

```
회의수당 9,000,000 + 상임위원 인건비 270,281,107 + 
사무국 인건비 5,405,622,143(60명×전체평균단가) + 
사무실임차료 356,400,000 = 6,041,303,250원(확정)
```
정답: 상임위원+비상임위원 3.7억 + 사무처인건비 23.41억(46명 별정직+14명
파견) + 자문위원 0.25억 + 보고서경비 2.06억 = 합계 29.41억원

**판정: 픽스처 버그는 고쳤지만, 그 결과 더 큰 프로덕션 문제가 드러남.**
우리 확정값(60.41억)이 정답(29.41억)의 **2.05배** — 사무국 인건비만 보면
54.06억 vs 23.41억으로 2.3배. 원인: 60명 전체에 "전체 공무원 평균"을
곱했는데, 실제 60명 중 14명(23%)은 파견 인력이라 원 소속기관이 인건비를
지급함("파견인력에 대한 인건비는 원 소속기관에서 지급하는 것으로 가정" —
로컬 DB에 3회 반복 확인된 NABO의 일관된 방침). **"파견 인력은 신규
재정소요에서 제외해야 한다"는 규칙 자체는 일반화 가능(n=3+)하지만, "몇
명이 파견이냐"의 비율은 사례마다 완전히 다름**(다른 위원회 2건 실측:
83.3% vs 40.4%, n=2로 이미 크게 벌어짐) — 대표값을 못 만들어서 규칙은
알아도 숫자는 못 채우는 상태로 남김. 미수정.
